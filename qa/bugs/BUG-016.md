# BUG-016: 'Keep editing' still closes the download dialog while a payment is in progress; the purchase is then recorded silently
Severity: S4
Priority: P1
Status: Open
Flow / TC-ID: Payments / download dialog, TC-REG-066
Devices: laptop-chrome, laptop-safari, laptop-firefox (phones run no keyboard cases; the button is the same code, not run there)
URL: /app/editor, Download PDF -> Pay step
Frequency: Always
Build / env: local isolated copy of the CURRENT working tree (branch resume-llm, uncommitted fixes on c53d3dc), vite dev on http://127.0.0.1:5473, fake Supabase, /api mocked, fake Razorpay, no live keys, 2026-11-25 IST

## Steps to reproduce
1. Signed in, no downloads left; Download PDF -> Continue -> 'Pay Rs 49 and continue' (fake Razorpay, no network).
2. While checkout is open, click 'Keep editing' in the dialog behind it.
3. Complete the fake payment.

## Expected
Same as Escape and scrim: ignored (or disabled) while busy, so the dialog is still there to show the result.
## Actual
The dialog closes (button is enabled during busy). The success handler still calls /api/downloads/purchase (purchaseAfterClose=1); the plan is granted with no dialog or message. This is the same outcome BUG-012 described, through a third close route.
## Evidence
- Test: qa/tests/regress2.spec.ts TC-REG-066 (annotation keep-editing-while-busy: buttonPresent=1 dialogClosed=true purchaseAfterClose=1)
## Probable cause
src/DownloadPaywall.jsx lines ~172 and ~222: the 'Keep editing' buttons use onClick={onClose} instead of closeUnlessBusy, and are not disabled while busy.
## Suggested fix
Use closeUnlessBusy (or disabled={busy}) on those buttons. Real Razorpay renders its own overlay; check on a real device in test mode.
